# Data dictionary

The canonical definitions and constraints are in `database/schema.sql`. UUID values are generated by PostgreSQL using `pgcrypto`.

| Table or view | Purpose | Important relationships and rules |
|---|---|---|
| `staff_users` | Staff identity and password hashes | Unique email; role is `admin` or `parking_staff`; inactive accounts cannot sign in |
| `parking_areas` | Facility address, capacity, rate and lifecycle status | Unique short code; non-negative rate; capacity must be positive |
| `parking_slots` | Individual spaces and current operational status | Belongs to one area; slot number is unique within its area |
| `drivers` | Driver identity and license details | Email, phone and license number are unique |
| `driver_phones` | Normalized driver phone numbers | References a driver; unique phone number; at most one primary number per driver |
| `vehicles` | Vehicle identity and descriptive details | Unique license plate; year and vehicle type are constrained |
| `driver_vehicles` | Current and historical driver/vehicle relationships | Supports reassignment; a driver/vehicle pair can have dated historical assignments |
| `allocations` | Vehicle check-in, slot assignment, check-out and charge | References one driver, vehicle and slot; only one active allocation per slot/vehicle |
| `check_in_out_events` | Audit trail for check-in and check-out actions | References allocation, driver, vehicle and slot |
| `occupancy_snapshot` | Optional historical occupancy observations | References area and slot; stores observation time and counts |
| `violation_types` | Configurable violation categories and default fines | Severity and non-negative default fine are constrained |
| `violations` | Fine records linked to parking sessions | Snapshot references to allocation, slot, vehicle and driver; creation is limited to active allocations |
| `payments` | Staff-recorded parking-fee or violation-fine transactions | Parking payments reference a checked-out allocation; payment category prevents mixing both purposes |
| `violation_payments` | Applies one violation-fine payment to one or more violations | Amount limits are checked under row locks; one payment may settle multiple fines |
| `notices` | Fine, reminder, dispute and overdue notice records | Unique event reference prevents duplicate notices; status is independent from violation status |
| `audit_outbox` | Durable PostgreSQL events pending delivery to MongoDB | Retries and publication state remain in PostgreSQL |
| `parking_area_occupancy` | Live area capacity and status aggregate | View over parking areas and slots; no duplicate availability flag |

`parking_slots.current_status` is the authoritative availability value. The original `is_available` compatibility column remains in the schema but is not used by application code.

`allocations.total_fee` is zero until check-out. Completed parking revenue is calculated from checked-out allocation records, not from violation payments.

The `payments` category/`allocation_id` relationship and its parking-fee trigger are added by `database/advanced_features.sql` for existing installations as well as fresh schema installs.

## Keys and lifecycle details

- `driver_vehicles.driver_vehicle_id` is the historical assignment key. `UNIQUE(driver_id, vehicle_id, assigned_from)` allows a later dated assignment without rewriting old rows.
- `driver_phones.phone_id` identifies a phone record; a partial unique index permits at most one primary phone per driver. It is added by `advanced_features.sql`.
- `allocations` has partial unique indexes on `slot_id` and `vehicle_id` for `status = 'active'`; historical sessions can reuse both.
- `payments.allocation_id` is required for `parking_fee` and NULL for `violation_fine`. `vehicle_id` is nullable. Payment methods describe staff-entered records, not gateway settlement.
- `violation_payments` is the link table for many-to-many settlement, unique on `(violation_id, payment_id)`. Amounts are positive and bounded by trigger checks under locks.
- `notices.violation_id` and `issued_by` are nullable in the schema; `driver_id` is required. Deleting a violation cascades to its notices, while deleting referenced staff is restricted.
- `occupancy_snapshot.allocation_id` is nullable and becomes NULL when its allocation is deleted. It is not the live occupancy source.
- `audit_outbox.aggregate_id` is a logical business identifier, not a foreign key. MongoDB `audit_logs.audit_id` is a unique copy of the outbox UUID; no cross-database foreign key exists.

## MongoDB audit document

| Field | Type / meaning |
|---|---|
| `audit_id` | String UUID copied from PostgreSQL outbox; unique index |
| `event_type`, `entity_type`, `entity_id` | Event name and logical business record reference |
| `actor_type`, `actor_id` | Actor metadata from the event payload, or system/database defaults |
| `occurred_at` | BSON date derived from outbox creation time |
| `payload` | Flexible business-event object; PostgreSQL stores the originating JSONB |
| `summary` | Human-readable event description |

`GET /api/audit/logs` deliberately omits `payload` and MongoDB `_id`. The diagram treats Mongo delivery as a logical copy, not a relational association. Field definitions in SQL and `src/lib/mongodb.ts` take precedence over this abbreviated dictionary.
